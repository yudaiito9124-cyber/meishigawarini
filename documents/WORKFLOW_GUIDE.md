## 💻 1. フロントエンド（画面）の開発とデプロイ

フロントエンドは「Next.js」というフレームワークで作られており、ホスティング（Web公開）には「AWS Amplify」を利用しています。

### 開発の手順（ローカルで画面を確認しながらコードを書く）

1. **フォルダを移動する**:
   ```bash
   cd frontend
   ```
2. **ローカルサーバーを起動する**:
   ```bash
   npm run dev
   ```
3. **確認する**:
   ブラウザで `http://localhost:3000` にアクセスします。コードを書き換えて保存すると、自動的に画面が更新されます。

### デプロイの手順（本番環境に反映させる）

フロントエンドは、**GitHubの `main` ブランチにコードを統合（マージ）するだけで自動的にデプロイ**されます。手動でコマンドを打つ必要はありません。

1. **コードの変更をコミットし、GitHubにプッシュする**:
   ```bash
   git add .
   git commit -m "フロントエンドの〇〇を修正"
   git push origin 作業ブランチ名
   ```
2. **GitHub上でPull Request (PR) を作成し、`main` にマージする**:
   マージされた瞬間に、AWS Amplifyが自動で最新のコードを読み取り、数分後に本番URLに反映されます。

## ⚙️ 2. バックエンド（インフラ・API）の開発とデプロイ

バックエンドは「AWS CDK」というツールを使って、インフラ構成（Lambda関数やDynamoDBなど）をコード（TypeScript）で管理しています。

### 開発の手順（コードを書いてエラーがないか確認する）

バックエンドのプログラム（`infra/lambda/`配下など）を変更した場合、AWSに上げる前に手元でコードの整合性をチェックします。

1. **フォルダを移動する**:
   ```bash
   cd infra
   ```
2. **AWSにログインする**:
   AWS環境を操作するための権限を取得します。（1日1回程度、またはセッション切れの際に実行します。※事前に `ACCOUNT_SETUP.md` の設定が完了している必要があります）
   ```bash
   aws login
   ```
3. **変更内容が正しいか（エラーが出ないか）をテスト・検証する**:
   ```bash
   npx cdk synth
   ```
   *※このコマンドは、書いたコードをAWSが理解できる形式に変換できるかをチェックします。エラーが出なければコードの実装は（文法的には）成功しています。*
4. **現在のAWS環境と、手元のコードの「差分」を確認する**:
   ```bash
   npx cdk diff
   ```
   *※「どこが追加され、どこが削除されるか」がターミナルに表示されます。意図しない変更（データベースの削除など）が含まれていないか必ず確認してください。*

### デプロイの手順（AWS本番環境に反映させる）

バックエンドの変更を実際のAWS環境に反映させるには、ターミナルから手動でデプロイコマンドを実行します。
*(※実行にはAWS CLIの認証設定が完了している必要があります)*

1. **AWSにログインする**:
   AWS環境を操作するための権限を取得します。（1日1回程度でOKです）
   ```bash
   aws login
   ```
2. **フォルダを移動していることを確認する**:
   ```bash
   cd infra
   ```
3. **デプロイを実行する**:
   ```bash
   npx cdk deploy
   ```
4. **確認プロンプトに答える**:
   セキュリティに関わる変更（権限の追加など）がある場合、途中で `Do you wish to deploy these changes (y/n)?` と聞かれます。内容を確認して **`y`** を入力し、Enterを押します。

> **⚠️ 注意事項**
> バックエンドのデプロイによって APIのURL や CognitoのID などが新しくなった場合は、フロントエンド側 (`frontend/.env.production` や `frontend/.env.staging`) も新しい値に書き換える必要があります。

## 🧪 3. テスト環境（Staging）の利用手順

本番環境（Production）とは独立したテスト用の環境（Staging）を利用できます。新しい機能を本番にマージする前に、ここで十分に動作確認を行ってください。

### バックエンド（インフラ）のテスト環境デプロイ
1.  **Staging用ブランチに切り替える**:
    ```bash
    git checkout stg
    ```
2.  **Staging環境へデプロイする**:
    `infra` フォルダで、`-c stage=stg` オプションを付けてデプロイします。
    ```bash
    cd infra
    npx cdk deploy -c stage=stg
    ```
    *※これにより、`infra/.env.stg` の設定が読み込まれ、本番とは別のデータベースやAPIが作成されます。*

### フロントエンドのテスト環境確認
1.  **環境変数の準備**: `frontend/.env.staging` に、Staging用のAPI URL等を設定します。
2.  **ローカルでの確認**: 以下のコマンドで接続先を切り替えて起動できます。
    ```bash
    cd frontend
    npm run dev:stg   # Staging環境へ接続
    npm run dev:prod  # 本格的な本番環境（または元々の設定）へ接続
    ```
    *※このコマンドを実行すると、`.env.staging` または `.env.production` の内容が `.env.local` に自動的にコピーされます。*

## 🚀 4. デプロイフローの推奨（ベストプラクティス）

1.  **開発**: 個別の作業ブランチで開発を行います。
2.  **テスト**: `stg` ブランチに統合し、`cdk deploy -c stage=stg` でStaging環境に反映させて動作確認します。
3.  **本番反映**: Stagingで問題がなければ、`master` ブランチに統合し、本番環境へデプロイします。

## トラブルシューティング（よくあるエラーと解決法）

### 「`npm install` や `npm ci` でエラーが出る」「Amplifyのビルドが失敗する」場合

複数の開発者がパッケージを追加・更新した際に、設定ファイル（`package.json`）と、実際のバージョンを記録したファイル（`package-lock.json`）の間に不整合（ズレ）が生じることがあります。
このズレが原因でエラーが起きている場合は、以下の手順で**「関連ファイルを一度すべて削除し、ゼロから再インストール（クリーンインストール）」**することで解決します。

1.  エラーが出ているフォルダ（`frontend` または `infra`）に移動します。
2.  以下のコマンドを実行し、一時ファイル群を強制的に削除します。
    ```bash
    # Windows の場合 (PowerShell)
    Remove-Item -Recurse -Force node_modules, package-lock.json
    
    # Mac / Linux の場合
    rm -rf node_modules package-lock.json
    ```
3.  依存関係をゼロから再解決してインストールします（これにより正しい `package-lock.json` が再生成されます）。
    ```bash
    npm install
    ```
4.  （確認用）クリーンインストールが正しく終了するか確認します。
    ```bash
    npm ci
    ```
これで不整合が解消され、エラーなくサーバー起動やビルド（デプロイ）ができるようになります。
